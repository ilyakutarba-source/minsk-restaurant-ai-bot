# Продукт и границы MVP

Редакция: 2026-10-01. Статус: спецификация для проверки scope, не отчёт о реализации. Документ фиксирует рабочие продуктовые решения для диплома одного Java/Spring студента. Новый PM-анализ не проводился.

## Vision, проблема и пользователь

Telegram-бот помогает выбрать заведение Минска и продолжить разговор о показанных вариантах: узнать меню, расписание, адрес и доступный рейтинг. Он связывает естественный язык с проверяемыми данными и объясняет, почему варианты соответствуют пожеланиям.

Основной пользователь планирует посещение один или с небольшой компанией и пользуется Telegram. Сейчас ему приходится сопоставлять кухню, бюджет, время и обстановку по нескольким источникам. Ценность бота — последовательный разговор с сохранением критериев и однозначной ссылкой «у второго».

Спрос именно на этого бота пока не подтверждён. Исходный вердикт ITERATE сохраняется: учебная ценность понятна, доступность данных и AI нужно проверить. Интервью и коммерческий анализ не являются новой задачей этой редакции.

Продукт не гарантирует свободный столик, наличие блюда, тишину или окончательный чек. Метки атмосферы выражают характеристику каталога, а не обещание обстановки в конкретный вечер.

## Core user journey

1. Пользователь: «Сегодня в 21:00 нас двое, до 150 BYN, итальянская кухня, хочется спокойно».
2. AI предлагает критерии; Java проверяет их. Недостающие или неоднозначные данные уточняются.
3. Search service возвращает до трёх подходящих заведений в стабильном порядке.
4. Пользователь видит короткое объяснение и фактические карточки с ориентировочным чеком.
5. После успешной отправки сохраняется именно показанный порядок.
6. «Что по меню у второго?» разрешается сервером в restaurantId и вызывает menu tool.
7. «До скольки работает первый?» вызывает details tool; факты читаются заново.
8. «А если нас четверо?» обновляет гостей, сохраняя остальные критерии, и запускает новый поиск.
9. /new очищает разговор, критерии и подборку.

Точные contracts, memory и reference resolution: [AI.md](AI.md). Правила поиска: [ARCHITECTURE.md](ARCHITECTURE.md#правила-поиска-и-рекомендаций).

## MVP — MUST

| Возможность | Граница первого релиза |
|---|---|
| Каталог | 10–12 реальных заведений Минска; первый slice — 3 |
| Пользовательский канал | Telegram private chats, русский язык, long polling |
| Посещение | 1–6 гостей; сегодня и следующие 6 дней; BYN |
| Поиск | Гости, общий бюджет, дата/время, кухня, поддерживаемые preferred tags |
| Бюджет | Собственный ориентировочный чек на одного гостя, источник и дата проверки |
| Меню | 5–10 полезных позиций на заведение; source, verifiedAt, coverage=PARTIAL |
| AI | Один provider/model; ChatClient, system prompt, tool calling, bounded chat memory |
| Tools | Ровно searchRestaurants, getRestaurantDetails, getRestaurantMenu |
| Объяснение | AI выбирает подтверждённые причины; Java контролирует фактические поля и безопасное отображение |
| Контекст | PostgreSQL memory по chatId + отдельные currentCriteria и последняя selection |
| Ссылки | Первый, второй, третий, последний, однозначное название; неоднозначность → уточнение |
| Команды | /start, /help, /new |
| Google | Rating, userRatingCount, текущие часы/статус, Maps link — если feasibility gate пройден |
| Проверка backend | Четыре REST endpoints + Swagger, без публичного AI chat API |
| Persistence | PostgreSQL, JPA/Hibernate, Flyway; H2 для части тестов |
| Качество | Содержательные JUnit/Mockito tests, PostgreSQL acceptance, 12 основных eval + 5 adversarial |
| Доставка | Compose app + postgres + persistent volume; Dokploy на VPS |

Числа, лимиты и диапазоны — принятые проектные границы, не результаты исследования.

Меню и подбор независимы: неполное или отсутствующее меню не исключает ресторан из поиска. Расчёт среднего чека из блюд не нужен. Правила происхождения чека и меню: [DATABASE.md](DATABASE.md#данные-и-их-происхождение).

Google — условная интеграция MVP, не зависимость basic search. TASK-00 допускает DEFERRED: live gate блокирует только TASK-10, не bootstrap/core slice; блокирующее значение и решение принадлежат [BACKLOG Open Gates](BACKLOG.md#open-gates). При окончательном исключении enrichment оформить явное решение и scope. Архитектура продолжает работать на собственных данных; stub нельзя представлять как live API.

## SHOULD HAVE после работающего MVP

- GitHub Actions: Maven verify и Docker build.
- Scheduled retention cleanup для неактивных разговоров.
- Пробное восстановление backup.
- Несколько текстовых Google reviews после проверки attribution/policy.
- Минимальные callbacks, если они действительно сокращают пользовательский путь.
- Исключения собственного расписания на конкретные праздничные даты.

Эти пункты не блокируют первую версию и не входят в TASK-00–TASK-14 как обязательные новые функции.

## COULD / Future Roadmap

После завершения дипломного MVP выбирать по одной подтверждённой потребности:

1. Пользовательская проверка пользы и языка объяснений.
2. Favorites; затем UserProfile и persistent preferences.
3. Recommendation history.
4. Geolocation и distance.
5. Admin panel/API со Spring Security.
6. Автоматический импорт одного подтверждённого формата меню.
7. Booking/Restoplace при доступном provider и явном сценарии.
8. Несколько городов, языков или AI providers.
9. RAG/vector DB только при отдельной доказанной задаче поиска по текстам.

## OUT OF SCOPE первого релиза

- Полный каталог Минска и копия полного меню.
- Favorites, профиль, постоянные предпочтения, история подборок.
- Геолокация, distance, несколько городов/providers.
- Сложные references, сравнение произвольных прошлых подборок, «тот итальянский, который дешевле предыдущего».
- Booking, оплата, Restoplace.
- Public AI chat REST, admin UI, Spring Security.
- Scraping и автоматическая синхронизация меню.
- Autonomous agent loop, дополнительные tools, AI SQL/JPA access.
- RAG, embeddings, vector DB.
- Redis/Kafka/RabbitMQ/Kubernetes, microservices, CQRS/event sourcing.
- Delivery state machine, exactly-once semantics, формальные RPO/RTO и enterprise backup policy.

## User Stories

### US-01 — Подобрать заведения

**Как:** пользователь Telegram.  
**Я хочу:** описать посещение обычным языком.  
**Чтобы:** получить несколько подходящих вариантов.

**Acceptance Criteria:**

- Поиск использует проверенные Java-критерии и возвращает только каталог.
- Показано не больше трёх вариантов в порядке search service.
- Чек подписан как ориентировочный и относится к указанному числу гостей.
- AI не меняет ID, названия, цены и порядок.

### US-02 — Уточнить и изменить пожелания

**Как:** пользователь.  
**Я хочу:** ответить короткой репликой или изменить один критерий.  
**Чтобы:** не вводить запрос заново.

**Acceptance Criteria:**

- Недостающие гости, бюджет, дата/время уточняются.
- Новый критерий заменяет соответствующее поле, остальные сохраняются.
- «К девяти» без вечернего контекста не превращается молча в 21:00.
- Другой chatId не влияет на критерии.

### US-03 — Получить объяснение

**Как:** пользователь.  
**Я хочу:** понять соответствие вариантов моим пожеланиям.  
**Чтобы:** выбрать осознанно.

**Acceptance Criteria:**

- Объяснение основано на reason codes, возвращённых Java.
- Не обещает гарантированную тишину, свободный столик или точный чек.
- Ошибка explanation call не уничтожает готовые factual cards.
- Текст короткий, без новых фактических полей.

### US-04 — Узнать меню второго

**Как:** пользователь.  
**Я хочу:** спросить о блюдах и ценах выбранного варианта.  
**Чтобы:** понять, что заказать.

**Acceptance Criteria:**

- «Второй» разрешён Java по последней успешно показанной selection.
- Используется menu tool правильного заведения.
- Видны source, verifiedAt и PARTIAL coverage.
- Нет позиции → «В сохранённой части меню такое блюдо не найдено».

### US-05 — Узнать подробности и рейтинг

**Как:** пользователь.  
**Я хочу:** узнать часы, адрес и доступные оценки заведения.  
**Чтобы:** проверить вариант перед посещением.

**Acceptance Criteria:**

- Details tool читает собственные факты заново.
- Live Google сведения помечены своим источником и временем получения.
- При Google failure собственная карточка остаётся доступной.
- Рейтинг отсутствует → значение не берётся из memory и не придумывается.

### US-06 — Начать заново

**Как:** пользователь.  
**Я хочу:** очистить текущий разговор.  
**Чтобы:** старые критерии и выбор больше не влияли на ответы.

**Acceptance Criteria:**

- /new очищает memory, критерии и SelectionItem.
- «Меню второго» после reset требует нового выбора.
- Новый разговор изолирован от старой generation.

### US-07 — Получить честный результат при ошибке

**Как:** пользователь.  
**Я хочу:** понимать отсутствие подходящих вариантов или данных.  
**Чтобы:** не принять выдуманный ответ за факт.

**Acceptance Criteria:**

- Пустой поиск не ослабляет hard constraints.
- AI/DB failure даёт понятное сообщение.
- Отсутствие меню не превращается в утверждение, что блюд нет.
- Booking не обещается и не исполняется.

### US-08 — Поддерживать учебный каталог

**Как:** куратор проекта.  
**Я хочу:** загрузить проверенные собственные данные.  
**Чтобы:** бот использовал объяснимые факты.

**Acceptance Criteria:**

- Контролируемый seed/import валидирует данные и не создаёт дубли.
- У чека, расписания и меню есть источники и даты.
- Частичное меню обозначено; блюда не используются для обязательного расчёта чека.
- В каталог добавлены 10–12 реальных заведений с конкретными филиалами.

## Definition of Done

Все пункты ниже — проверки будущей реализации, сейчас не выполнены.

- [ ] Clean checkout собирается; совместимые версии pinned по результату TASK-00.
- [ ] PostgreSQL запускается; Flyway создаёт схему; Hibernate validate проходит.
- [ ] Есть 10–12 реальных заведений с проверяемыми собственными источниками.
- [ ] У ориентировочного чека есть смысл «на одного», source и verifiedAt.
- [ ] Частичные меню содержат 5–10 полезных позиций, source и verifiedAt.
- [ ] Поиск работает независимо от полноты меню; ranking детерминирован.
- [ ] Telegram long polling работает в личных чатах.
- [ ] Spring AI реально выбирает и вызывает три tools через application services.
- [ ] AI не имеет SQL/JPA-доступа; factual cards формирует Java.
- [ ] Контролируемое AI-объяснение работает; его отказ оставляет фактическую выдачу.
- [ ] Chat memory изолирована по chatId и переживает restart.
- [ ] /new очищает memory/state/selection; «меню второго» работает по показанному порядку.
- [ ] Google enrichment проверен live либо официально исключён после failed TASK-00 gate.
- [ ] Google failure не ломает поиск; Google content не сохраняется в memory/каталоге произвольно.
- [ ] Четыре REST endpoints и Swagger доступны в непубличной конфигурации.
- [ ] Основные unit/integration tests и PostgreSQL acceptance проходят.
- [ ] Eval соответствует простым критериям [AI.md](AI.md#ai-eval).
- [ ] Docker Compose работает; Dokploy deployment на VPS воспроизводим.
- [ ] Persistent PostgreSQL volume переживает restart/redeploy; приложение поднимается после restart.
- [ ] Документирован способ backup; restore drill не является обязательным gate.
- [ ] Секретов нет в Git, образах и обычных логах.
- [ ] README будущей реализации позволяет повторить настройку, запуск и демонстрацию.
- [ ] Проведена репетиция защиты; студент объясняет границы AI/Java/DB.

TTL, CI/CD, callbacks и production delivery guarantees не являются условиями DoD.

| Время | Действие | Что подтверждает |
|---|---|---|
| 0:00–1:00 | Проблема, scope, схема архитектуры | Понятный дипломный сценарий |
| 1:00–2:00 | Compose/Dokploy, PostgreSQL, Flyway | Воспроизводимый deployment |

Дата и время demo подбираются под проверенное расписание. В failed Google gate ветке показать решение об исключении и собственные details. Stub и заранее записанные ответы не выдаются за live-интеграцию. Не показывать токены, секреты и внутренние рассуждения модели.
